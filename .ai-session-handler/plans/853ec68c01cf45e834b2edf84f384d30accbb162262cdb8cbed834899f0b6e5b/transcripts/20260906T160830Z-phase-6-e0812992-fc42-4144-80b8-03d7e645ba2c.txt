[codex] # Service-Common Artifact Resolution
[codex] 
[codex] This document explains the split between local `mavenLocal()` resolution and
[codex] the GitHub Packages path used by GitHub Actions and release builds.
[codex] 
[codex] ## Version Scope
[codex] 
[codex] `service-common` is a shared Java library version, not the deployment version
[codex] for the whole Budget Analyzer stack. Bump and release it when
[codex] `spring-platform`, `spring-cloud-platform`, `service-core`, or `service-web`
[codex] changes. Do not change it only because a service image, frontend artifact,
[codex] route, production overlay, `/api-docs` metadata file, or OCI deployment
[codex] configuration changed.
[codex] 
[codex] Java services can release runtime artifacts while continuing to consume the
[codex] same checked-in `serviceCommon` coordinate from `gradle/libs.versions.toml`.
[codex] The production deployment identity is the digest-pinned image inventory and
[codex] deployment manifest, which may contain mixed service artifact versions.
[codex] 
[codex] ## Local Contributor Flow
[codex] 
[codex] The supported side-by-side workspace flow must stay credential-free.
[codex] 
[codex] If you follow [getting-started.md](getting-started.md) and run local
[codex] development through orchestration and Tilt:
[codex] 
[codex] - clone the repos side by side
[codex] - open the sibling `orchestration/` repo
[codex] - run `./setup.sh`
[codex] - run `tilt up`
[codex] 
[codex] you should not need `GITHUB_ACTOR`, `GITHUB_TOKEN`, or a personal access token
[codex] just to start the app locally.
[codex] 
[codex] That works because the local build path stays local-first:
[codex] 
[codex] - Java service repos keep `mavenLocal()` first
[codex] - Tilt runs the `service-common-publish` resource first
[codex] - `service-common-publish` runs `publishToMavenLocal`
[codex] - downstream host-side Gradle builds then resolve `service-common` from Maven
[codex]   Local
[codex] 
[codex] If you hit a local `service-common` resolution error while working in the full
[codex] workspace, republish it locally and rerun the service build:
[codex] 
[codex] ```bash
[codex] cd ../service-common
[codex] ./gradlew clean build publishToMavenLocal
[codex] ```
[codex] 
[codex] ## When GitHub Packages Credentials Are Required
[codex] 
[codex] GitHub Packages credentials are a CI/release concern, not a getting-started
[codex] prerequisite.
[codex] 
[codex] You need GitHub Packages credentials when all of these are true:
[codex] 
[codex] - the build is not using the local orchestration/Tilt path
[codex] - `service-common` is not already available through Maven Local
[codex] - the build must resolve the published `org.budgetanalyzer` artifacts remotely
[codex]   from `https://maven.pkg.github.com/budgetanalyzer/service-common`
[codex] 
[codex] Typical examples:
[codex] 
[codex] - default GitHub Actions `build.yml` runs in `transaction-service`,
[codex]   `currency-service`, `permission-service`, and `session-gateway`
[codex] - release-image Docker builds
[codex] - isolated CI or clean-builder image builds
[codex] - manual clean-shell verification of remote published artifacts
[codex] 
[codex] `service-common` itself now refreshes the current checked-in snapshot from
[codex] `main` through its `publish-snapshot.yml` workflow. That remote snapshot path
[codex] exists to support isolated CI/release builds; it does not change the local
[codex] contributor contract.
[codex] 
[codex] For the Java consumer repos, the default build workflow contract is now:
[codex] 
[codex] - read the pinned `serviceCommon` version from `gradle/libs.versions.toml`
[codex] - fail fast if `SERVICE_COMMON_PACKAGES_USERNAME` or
[codex]   `SERVICE_COMMON_PACKAGES_READ_TOKEN` is missing
[codex] - preflight the versioned `service-core` and `service-web` POM URLs in GitHub
[codex]   Packages
[codex] - run `./gradlew build` with `GITHUB_ACTOR` / `GITHUB_TOKEN` exported from
[codex]   that same secret pair
[codex] 
[codex] ## GitHub Actions Environment
[codex] 
[codex] When a workflow intentionally resolves `service-common` remotely from GitHub
[codex] Packages, Gradle needs both a token and a package username.
[codex] 
[codex] For cross-repo private Maven/Gradle consumption, do not assume the workflow
[codex] repo's own `GITHUB_TOKEN` can read `service-common`. GitHub still treats these
[codex] packages as repository-scoped, so the consuming workflow needs an explicit
[codex] GitHub Packages credential.
[codex] 
[codex] In GitHub Actions, the current repo wiring expects:
[codex] 
[codex] ```yaml
[codex] env:
[codex]   GITHUB_ACTOR: ${{ secrets.SERVICE_COMMON_PACKAGES_USERNAME }}
[codex]   GITHUB_TOKEN: ${{ secrets.SERVICE_COMMON_PACKAGES_READ_TOKEN }}
[codex] ```
[codex] 
[codex] `GITHUB_ACTOR` here means the username that owns the GitHub Packages credential,
[codex] not necessarily `${{ github.actor }}`. `GITHUB_TOKEN` here means the secret used
[codex] for remote package reads, not necessarily the workflow repo's default token.
[codex] This requirement applies to the remote GitHub Packages path used by default
[codex] `build.yml` and release workflows. It does not apply to the normal `tilt up`
[codex] contributor flow.
[codex] 
[codex] ## Containerized Release Builds
[codex] 
[codex] The Java service Dockerfiles now support remote `service-common` resolution for
[codex] release and isolated CI builds without copying host `.m2` state into the build
[codex] context and without checking out sibling source trees.
[codex] 
[codex] Pass the workflow credentials into BuildKit as secrets:
[codex] 
[codex] ```bash
[codex] docker build \
[codex]   --secret id=github_actor,env=GITHUB_ACTOR \
[codex]   --secret id=github_token,env=GITHUB_TOKEN \
[codex]   -f Dockerfile .
[codex] ```
[codex] 
[codex] In GitHub Actions, the release job should still expose those same credential
[codex] values under the env names the current Gradle builds read:
[codex] 
[codex] ```yaml
[codex] env:
[codex]   GITHUB_ACTOR: ${{ secrets.SERVICE_COMMON_PACKAGES_USERNAME }}
[codex]   GITHUB_TOKEN: ${{ secrets.SERVICE_COMMON_PACKAGES_READ_TOKEN }}
[codex] ```
[codex] 
[codex] The Dockerfiles read those values only inside the Gradle builder-stage `RUN`
[codex] steps, so the credentials are not written into the image, filesystem layers, or
[codex] checked-in repo files.
[codex] 
[codex] ## Why Public Package Visibility Does Not Remove This

[codex] Making the `service-common` Maven packages public in the GitHub UI does not
[codex] remove the Maven/Gradle authentication requirement.
[codex] 
[codex] Keep the release workflow package-visibility and workflow-access cleanup, but do not
[codex] treat it as the fix for local contributor UX. The fix for local contributor UX
[codex] is keeping the side-by-side workspace and Tilt flow local-first and
[codex] credential-free.

[codex] # Transaction Service
[codex] 
[codex] > Repository operating instructions: [AGENTS.md](AGENTS.md#repository-position)
[codex] 
[codex] [![Build](https://github.com/budgetanalyzer/transaction-service/actions/workflows/build.yml/badge.svg)](https://github.com/budgetanalyzer/transaction-service/actions/workflows/build.yml)
[codex] 
[codex] Spring Boot microservice for managing financial transactions in Budget Analyzer - a reference architecture for microservices.
[codex] 
[codex] ## Overview
[codex] 
[codex] The Transaction Service is responsible for:
[codex] 
[codex] - Managing financial transactions
[codex] - Importing transactions from CSV and PDF statement files
[codex] - Supporting multi-account and multi-currency transaction records
[codex] - Providing saved transaction views and advanced search
[codex] 
[codex] ## Features
[codex] 
[codex] - RESTful API for transaction management
[codex] - PostgreSQL persistence with Flyway migrations
[codex] - OpenAPI/Swagger documentation
[codex] - CSV and PDF transaction import
[codex] - Duplicate detection for preview-to-batch imports
[codex] - Static saved transaction views with explicit membership
[codex] - JPA/Hibernate for data access
[codex] - Spring Boot Actuator for health checks
[codex] - Input validation and error handling
[codex] 
[codex] ## Technology Stack
[codex] 
[codex] - **Java 25**
[codex] - **Spring Boot 3.x**
[codex]   - Spring Web (REST APIs)
[codex]   - Spring Data JPA (database access)
[codex]   - Spring Boot Actuator (monitoring)
[codex]   - Spring Validation
[codex] - **PostgreSQL** (database)
[codex] - **Flyway** (database migrations)
[codex] - **SpringDoc OpenAPI** (API documentation)
[codex] - **JUnit 5** (testing)

[codex] ## Integration
[codex] 
[codex] This service integrates with:
[codex] - **[Session Gateway](https://github.com/budgetanalyzer/session-gateway)** and **Envoy ext_authz** — Session Gateway manages browser authentication and Redis-backed sessions; Envoy ext_authz validates those sessions and injects pre-validated `X-User-Id`, `X-Roles`, and `X-Permissions` headers before requests reach the service
[codex] - **API Gateway** (Envoy + NGINX) for routing and session enforcement
[codex] - **PostgreSQL** for data persistence
[codex] - **[Service Common](https://github.com/budgetanalyzer/service-common)** for the shared Spring platform and runtime utilities (including claims-header security that reads pre-validated headers from ext_authz)
[codex] - **[Permission Service](https://github.com/budgetanalyzer/permission-service)** for fine-grained claims-header-based authorization (roles and atomic permissions like `transactions:read`, `transactions:write`)
[codex] 
[codex] See the [orchestration repository](https://github.com/budgetanalyzer/orchestration) for full system setup.

[codex] ## Purpose
[codex] 
[codex] Multi-module Gradle project providing shared dependency platforms and runtime libraries for all Budget Analyzer Spring Boot microservices. Publishes four artifacts:
[codex] 
[codex] **spring-platform**: Base backend Spring dependency platform (Spring Boot BOM, Spring Modulith BOM, shared JVM constraints)
[codex] **spring-cloud-platform**: Opt-in Spring Cloud dependency platform overlay
[codex] **service-core**: Minimal-dependency core utilities (base entities, CSV parsing, safe logging)
[codex] **service-web**: Spring Boot web components (exception handling, API error responses, HTTP logging, OpenAPI config)
[codex] 
[codex] **Impacts**: Current consumers are discoverable from the workspace, and changes here affect all services that depend on these libraries.
[codex] 
[codex] ## Module Architecture
[codex] 
[codex] ### spring-platform
[codex] **Location**: `spring-platform/build.gradle.kts`
[codex] 
[codex] **Purpose**: Base Maven BOM-style dependency platform for Budget Analyzer Spring services
[codex] 
[codex] **Contains**:
[codex] - Spring Boot dependency BOM import
[codex] - Spring Modulith dependency BOM import
[codex] - Shared constraints for SpringDoc, Testcontainers, WireMock, Awaitility, and ShedLock
[codex] 
[codex] **Behavior**: Version management only. No source code, runtime dependencies, beans, or autoconfiguration metadata.
[codex] 
[codex] ### spring-cloud-platform
[codex] **Location**: `spring-cloud-platform/build.gradle.kts`
[codex] 
[codex] **Purpose**: Opt-in Maven BOM-style dependency platform for services using Spring Cloud APIs
[codex] 
[codex] **Contains**:
[codex] - spring-platform import
[codex] - Spring Cloud dependency BOM import
[codex] 
[codex] **Behavior**: Version management only. Use only in services that explicitly depend on Spring Cloud libraries.
[codex] 
[codex] ### service-core
[codex] **Location**: `service-core/src/main/java/org/budgetanalyzer/core/`
[codex] 
[codex] **Purpose**: Domain-agnostic utilities with minimal dependencies
[codex] 
[codex] **Contains**:
[codex] - `domain/` - Base JPA entities (AuditableEntity, SoftDeletableEntity)
[codex] - `repository/` - Repository utilities (SoftDeleteOperations)
[codex] - `csv/` - CSV parsing (CsvParser, CsvData, OpenCsvParser)
[codex] - `logging/` - Safe logging utilities (`SafeLogger`, `@Sensitive`, `QueryParamSanitizer`, `HttpBodyLogSanitizer`, `SensitiveHeaderMasker`)
[codex] 
[codex] **Dependencies**: Spring Data JPA, Spring Boot Actuator, Jackson, SLF4J, OpenCSV
[codex] 
[codex] ### service-web
[codex] **Location**: `service-web/src/main/java/org/budgetanalyzer/service/`
[codex] 
[codex] **Purpose**: Spring Boot web components supporting both servlet and reactive stacks
[codex] 
[codex] **Contains**:
[codex] - `api/` - Shared error response models (ApiErrorResponse, ApiErrorType, FieldError, ApiExceptionHandler)
[codex] - `exception/` - Exception hierarchy (shared by both stacks: ResourceNotFoundException, BusinessException, etc.)
[codex] - `config/` - Shared configuration (HttpLoggingProperties, ServiceWebAutoConfiguration, BaseOpenApiConfig)
[codex] - `servlet/` - Servlet-specific implementations (Spring MVC)
[codex]   - `http/` - HTTP filters (CorrelationIdFilter, HttpLoggingFilter, ContentLoggingUtil, HttpLoggingConfig)
[codex]   - `api/` - Exception handler (ServletApiExceptionHandler)
[codex] - `reactive/` - Reactive-specific implementations (Spring WebFlux)
[codex]   - `http/` - Reactive filters (ReactiveCorrelationIdFilter, ReactiveHttpLoggingFilter, body caching decorators, ReactiveHttpLoggingConfig)
[codex]   - `api/` - Exception handler (ReactiveApiExceptionHandler)
[codex] 
[codex] **Dependencies**: service-core (transitive), Spring Boot Starter Web (compileOnly), Spring Boot Starter WebFlux (compileOnly), SpringDoc OpenAPI (compileOnly)
[codex] 
[codex] **Note**: service-web supports BOTH servlet and reactive stacks through conditional autoconfiguration.
[codex] 
[codex] **Note**: Actuator comes from service-core, available to all services (web and non-web).
[codex] 
[codex] **Note**: service-web transitively includes service-core, so consuming services typically only need service-web.
[codex]

[codex] ## Spring Boot Conventions
[codex] 
[codex] **THE canonical source of truth** for Spring Boot patterns across all Budget Analyzer microservices.
[codex] 
[codex] **Pattern**: Clean layered architecture (Controller → Service → Repository) with standardized naming, pure JPA persistence, and base entity classes for common functionality.
[codex] 
[codex] **When to consult details**:
[codex] - Setting up new service → Read [Architecture Layers](docs/spring-boot-conventions.md#architecture-layers) and [Package Structure](docs/spring-boot-conventions.md#package-structure)
[codex] - Creating entities → Read [Base Entity Classes](docs/spring-boot-conventions.md#base-entity-classes) (AuditableEntity, SoftDeletableEntity)
[codex] - Writing controllers → Read [HTTP Response Patterns](docs/spring-boot-conventions.md#http-response-patterns) (201 Created with Location header)
[codex] - Dependency injection → Read [Dependency Injection](docs/spring-boot-conventions.md#dependency-injection) section
[codex] 
[codex] **Quick reference**:
[codex] - Controllers: `*Controller` + `@RestController` + thin (HTTP concerns only)
[codex] - Services: `*Service` concrete classes + `@Service` + `@Transactional` at this layer
[codex] - Repositories: `*Repository` extends `JpaRepository&lt;Entity, ID>`
[codex] - Providers: `*Provider` interface + implementation (for external service boundaries only)
[codex] - Pure JPA only: **Forbidden** `org.hibernate.*` → **Use** `jakarta.persistence.*`
[codex] - Base entities: Extend `AuditableEntity` (timestamps) or `SoftDeletableEntity` (soft delete)
[codex] 
[codex] **For comprehensive patterns, read [docs/spring-boot-conventions.md](docs/spring-boot-conventions.md) when working on architecture tasks.**

[codex] # Service-Common Artifact Resolution
[codex] 
[codex] This document explains the split between local `mavenLocal()` resolution and
[codex] the GitHub Packages path used by GitHub Actions and release builds.
[codex] 
[codex] ## Version Scope
[codex] 
[codex] `service-common` is a shared Java library version, not the deployment version
[codex] for the whole Budget Analyzer stack. Bump and release it when
[codex] `spring-platform`, `spring-cloud-platform`, `service-core`, or `service-web`
[codex] changes. Do not change it only because a service image, frontend artifact,
[codex] route, production overlay, `/api-docs` metadata file, or OCI deployment
[codex] configuration changed.
[codex] 
[codex] Java services can release runtime artifacts while continuing to consume the
[codex] same checked-in `serviceCommon` coordinate from `gradle/libs.versions.toml`.
[codex] The production deployment identity is the digest-pinned image inventory and
[codex] deployment manifest, which may contain mixed service artifact versions.
[codex] 
[codex] ## Local Contributor Flow
[codex] 
[codex] The supported side-by-side workspace flow must stay credential-free.
[codex] 
[codex] If you follow [getting-started.md](getting-started.md) and run local
[codex] development through orchestration and Tilt:
[codex] 
[codex] - clone the repos side by side
[codex] - open the sibling `orchestration/` repo
[codex] - run `./setup.sh`
[codex] - run `tilt up`
[codex] 
[codex] you should not need `GITHUB_ACTOR`, `GITHUB_TOKEN`, or a personal access token
[codex] just to start the app locally.
[codex] 
[codex] That works because the local build path stays local-first:
[codex] 
[codex] - Java service repos keep `mavenLocal()` first
[codex] - Tilt runs the `service-common-publish` resource first
[codex] - `service-common-publish` runs `publishToMavenLocal`
[codex] - downstream host-side Gradle builds then resolve `service-common` from Maven
[codex]   Local
[codex] 
[codex] If you hit a local `service-common` resolution error while working in the full
[codex] workspace, republish it locally and rerun the service build:
[codex] 
[codex] ```bash
[codex] cd ../service-common
[codex] ./gradlew clean build publishToMavenLocal
[codex] ```
[codex] 
[codex] ## When GitHub Packages Credentials Are Required
[codex] 
[codex] GitHub Packages credentials are a CI/release concern, not a getting-started
[codex] prerequisite.
[codex] 
[codex] You need GitHub Packages credentials when all of these are true:
[codex] 
[codex] - the build is not using the local orchestration/Tilt path
[codex] - `service-common` is not already available through Maven Local
[codex] - the build must resolve the published `org.budgetanalyzer` artifacts remotely
[codex]   from `https://maven.pkg.github.com/budgetanalyzer/service-common`
[codex] 
[codex] Typical examples:
[codex] 
[codex] - default GitHub Actions `build.yml` runs in `transaction-service`,
[codex]   `currency-service`, `permission-service`, and `session-gateway`
[codex] - release-image Docker builds
[codex] - isolated CI or clean-builder image builds
[codex] - manual clean-shell verification of remote published artifacts
[codex] 
[codex] `service-common` itself now refreshes the current checked-in snapshot from
[codex] `main` through its `publish-snapshot.yml` workflow. That remote snapshot path
[codex] exists to support isolated CI/release builds; it does not change the local
[codex] contributor contract.
[codex] 
[codex] For the Java consumer repos, the default build workflow contract is now:
[codex] 
[codex] - read the pinned `serviceCommon` version from `gradle/libs.versions.toml`
[codex] - fail fast if `SERVICE_COMMON_PACKAGES_USERNAME` or
[codex]   `SERVICE_COMMON_PACKAGES_READ_TOKEN` is missing
[codex] - preflight the versioned `service-core` and `service-web` POM URLs in GitHub
[codex]   Packages
[codex] - run `./gradlew build` with `GITHUB_ACTOR` / `GITHUB_TOKEN` exported from
[codex]   that same secret pair
[codex] 
[codex] ## GitHub Actions Environment
[codex] 
[codex] When a workflow intentionally resolves `service-common` remotely from GitHub
[codex] Packages, Gradle needs both a token and a package username.
[codex] 
[codex] For cross-repo private Maven/Gradle consumption, do not assume the workflow
[codex] repo's own `GITHUB_TOKEN` can read `service-common`. GitHub still treats these
[codex] packages as repository-scoped, so the consuming workflow needs an explicit
[codex] GitHub Packages credential.
[codex] 
[codex] In GitHub Actions, the current repo wiring expects:
[codex] 
[codex] ```yaml
[codex] env:
[codex]   GITHUB_ACTOR: ${{ secrets.SERVICE_COMMON_PACKAGES_USERNAME }}
[codex]   GITHUB_TOKEN: ${{ secrets.SERVICE_COMMON_PACKAGES_READ_TOKEN }}
[codex] ```
[codex] 
[codex] `GITHUB_ACTOR` here means the username that owns the GitHub Packages credential,
[codex] not necessarily `${{ github.actor }}`. `GITHUB_TOKEN` here means the secret used
[codex] for remote package reads, not necessarily the workflow repo's default token.
[codex] This requirement applies to the remote GitHub Packages path used by default
[codex] `build.yml` and release workflows. It does not apply to the normal `tilt up`
[codex] contributor flow.
[codex] 
[codex] ## Containerized Release Builds
[codex] 
[codex] The Java service Dockerfiles now support remote `service-common` resolution for
[codex] release and isolated CI builds without copying host `.m2` state into the build
[codex] context and without checking out sibling source trees.
[codex] 
[codex] Pass the workflow credentials into BuildKit as secrets:
[codex] 
[codex] ```bash
[codex] docker build \
[codex]   --secret id=github_actor,env=GITHUB_ACTOR \
[codex]   --secret id=github_token,env=GITHUB_TOKEN \
[codex]   -f Dockerfile .
[codex] ```
[codex] 
[codex] In GitHub Actions, the release job should still expose those same credential
[codex] values under the env names the current Gradle builds read:
[codex] 
[codex] ```yaml
[codex] env:
[codex]   GITHUB_ACTOR: ${{ secrets.SERVICE_COMMON_PACKAGES_USERNAME }}
[codex]   GITHUB_TOKEN: ${{ secrets.SERVICE_COMMON_PACKAGES_READ_TOKEN }}
[codex] ```
[codex] 
[codex] The Dockerfiles read those values only inside the Gradle builder-stage `RUN`
[codex] steps, so the credentials are not written into the image, filesystem layers, or
[codex] checked-in repo files.
[codex] 
[codex] ## Why Public Package Visibility Does Not Remove This
[codex] 
[codex] Making the `service-common` Maven packages public in the GitHub UI does not
[codex] remove the Maven/Gradle authentication requirement.
[codex] 
[codex] Keep the release workflow package-visibility and workflow-access cleanup, but do not
[codex] treat it as the fix for local contributor UX. The fix for local contributor UX
[codex] is keeping the side-by-side workspace and Tilt flow local-first and
[codex] credential-free.
